# 2026-10-26 — modem and SIM on 7.3 gpu1

**Goal.** With a SIM in the phone, find out whether the modem registers on the
flashed 7.3 kernel (gpu1), without changing the kernel or touching EFS.
**Phone.** OnePlus 13 (CPH2653). No serial, IMEI or SIM numbers here.
**Kernel.** `7.3.0-rc6-dodge-gpu1` (flashed boot_a). Its DT has the `mpss` node enabled.
**Result.** Stopped. The SIM reads and needs no PIN, but the modem stays
offline with no RF bands: no registration, no signal, no data.

## What we did

1. `touch /etc/omamobile/modem-probe.enable`, removed the modem lines from the
   gpu1 `skip-units`, rebooted (gate first). `omamobile-modem rmtfs-mem` needed a
   7.x fallback: the 6.16 `qcom_rmtfs_mem.ko` is not in the gpu1 overlay, so it
   now loads the in-tree `rmtfs_mem.ko` from `/usr/lib/modules/<release>.held`.
2. rmtfs ran only as `rmtfs -r -o /var/lib/omamobile/modem-efs -v` (read-only
   copies, writes kept in RAM). tqftpserv served MCFG from `/lib/firmware`.
3. `qmicli -p -d qrtr://0`: DMS operating mode, NAS system selection, PDC
   configs, UIM card status. No SMS, no calls, no PIN entered.
4. A tqftpserv debug run (a drop-in with `-d`, removed afterwards) showed every
   file request the modem made.

## What happened

- **MPSS:** remoteproc `running`; QMI over QRTR answers; ModemManager sees a
  QMI modem with the fake net port.
- **SIM:** the physical SIM is in slot 1 and reads fine, operator TELMORE.
  PIN1 is disabled (retries untouched). ModemManager reports `sim-pin2`
  (PIN2 is only for fixed dialing; it doesn't block). ModemManager defaulted to
  slot 2 (the empty eUICC); `--uim-set-primary-sim-slot=1` failed (QMI
  Internal), but activating the primary GW provisioning session on slot 1 with
  `--uim-change-provisioning-session` (AID read from card status) works. It
  does not persist across a reboot.
- **Offline:** DMS operating mode is `offline` from boot. `online` and
  `low-power` both fail with InvalidTransition. NAS shows no bands. PDC has no
  platform (hardware) MCFG; the software MCFG for the operator's network
  (TDC Denmark commercial) is selected automatically and active. tqftpserv
  satisfies every request and the modem never asks for an `mcfg_hw` or RF
  file. Likely cause: the RF/hardware config the modem expects (stock gets it
  from persist RFS or its own HW MCFG handling) is missing.
- **Stopping the MPSS resets the phone:** `echo stop` on the modem remoteproc
  hard-resets the phone at once, with nothing in the kernel log. The unit's
  old ExecStop does the same write, so a shutdown with the modem running
  would reset too (not tried). EFS partitions and the copies were checked
  afterwards: unchanged. Since then a runtime drop-in with an empty
  `ExecStop=` goes in before any reboot with the modem running, and those
  reboots are clean.
- Applying a different MCFG needs a modem reset, and that is the same stop.
  rmtfs `-r` also drops its RAM changes on a reset.

## Learning

- The modem does not need any kernel or dts change to boot on 7.3, but it is
  not usable until the RF/HW config is solved. Next: look at what stock loads
  from persist RFS and how Android selects the HW MCFG. Reading persist needs
  Martin's approval (partition is off limits).
- The modem unit has no ExecStop now and `omamobile-modem stop` only logs.
- The PR branch keeps `mpss` disabled; that stays right. The PR text now says
  the MPSS boots but stays offline, and that stopping it resets the phone.
- The phone is back flagless (`/etc/omamobile` has only `sensors.enable`).
