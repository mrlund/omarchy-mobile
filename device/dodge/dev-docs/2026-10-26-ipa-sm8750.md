# IPA on SM8750 (dodge, 7.3): research and trial

2026-10-26, from 13:08 CET. Goal: give the modem an IPA data path, so it
stops asserting `DS_3GPP_BEARER_SWITCH_COMPLETE_IND not rcvd from DS in
2600ms` about 30 s after LTE registration
([2026-10-26-modem-efs-rw-73.md](2026-10-26-modem-efs-rw-73.md)), and, if
possible, pass mobile data. The PR branch `omamobile-dodge` (`952dec326`)
stays as it is. All kernel work goes on the local branch `trial/ipa`.

## Findings (written before any code)

### Which IPA: v5.5 (5.5.2)

- The stock live DT (`rooted-2026-10-15-on/live.dts`) has `ipa_hw:
  qcom,ipa@3e00000` with `qcom,ipa-hw-ver = <0x18>`. In OnePlus' SM8750
  dataipa source (`OnePlusOSS/android_kernel_modules_and_devicetree_oneplus_sm8750`,
  `d50b305f7`, `vendor/qcom/opensource/dataipa/drivers/platform/msm/include/uapi/linux/msm_ipa.h:1060`),
  `IPA_HW_v5_5 = 24` = 0x18.
- The modem partition (`modem_a`, mounted read-only) ships
  `image/fw_ipa_gsi_5.5_p.elf` next to `ipa_fws.mdt` and `ipa_fws.b00`-`b04`.
- Konrad Dybcio (Qualcomm), on lore in reply to the Eliza IPA RFC
  (2026-04-17): "8650 -> v5.5.1; eliza, 8750 and a couple others -> 5.5.2".
- Upstream `drivers/net/ipa` in our 7.3-rc6 tree supports v5.5
  (`qcom,sm8550-ipa`, `ipa_data-v5.5.c`); SM8650 uses
  `"qcom,sm8650-ipa", "qcom,sm8550-ipa"`. SM8750 has no IPA node upstream.

### Configuration data: what upstream v5.5 gets wrong for SM8750

The reference is OnePlus' `ipa_v3/ipa_utils.c` (same commit):
- **Memory layout** (`ipa_5_5_mem_part`, line 6698): uses 68 Q6 FnR
  counters (`ipa_i.h:96`, `IPA_Q6_FNR_IDX_CNT (68)`), so `stats_fnr` is
  `0x2cd0`+`0xc40`, `stats_drop` `0x3910`, `modem` `0x3938`+`0xd48`,
  `nat_tbl` `0x4680`, `pdn_config` `0x4f88`+`0x50`, end `0x4fd8`. Upstream
  v5.5 still has the old 52-counter layout (CodeLinaro dataipa `0a3c432e4`,
  "ipa: increase q6 fnr counters", Feb 2024, changed it).
- **Endpoints** (`ipa3_ep_mapping[IPA_5_5]`): APPS_LAN_CONS 17/ch 14,
  APPS_WAN_CONS 24/ch 1, Q6_WAN_CONS 22/ch 7, APPS_CMD_PROD 14/ch 12,
  APPS_WAN_PROD 2/ch 11, Q6_WAN_PROD 12/ch 0, Q6_DL_NLO_DATA_PROD 15/ch 2.
  Upstream has LAN_RX 16/ch 13, AP_MODEM_RX 23 and MODEM_AP_RX 21.
- **QSB** (line 1041): `[IPA_5_5][DDR] = {16, 12, 0}`,
  `[PCIE] = {16, 8, 0}` (reads, writes, read beats). Upstream has
  reads and writes swapped.
- Alexander Koskovich's RFC "net: ipa: add support for Eliza SoC (IPA 5.5)"
  (lore `20260416-eliza-ipa-v1-0-f4109a8e43c4@pm.me`, not merged) fixes all
  three:
  - patch 2/4 fixes the endpoints and QSB for v5.5;
  - patch 4/4 adds `ipa_data_v5_5_eliza` with the 68-counter memory table;
  - patch 3/4 adds the QMI "HW filter stats info" request. Per the cover
    letter, without it the system halts shortly after IPA starts on Eliza.

  The Eliza memory table is identical, offset for offset, to OnePlus'
  SM8750 `ipa_5_5_mem_part`, and patch 2's endpoint numbers match the SM8750
  mapping. So SM8750 can use the Eliza data unchanged.
- The GSI v5.0+ event ring fix (upstream `56007972c0b1`, `CH_ERINDEX` in
  `CH_C_CNTXT_1`) is already in our tree (`gsi.c:849`).

### Device tree (derived, nothing guessed)

Downstream `data-devicetree/sun-ipa.dtsi` (SM8750) and
`pineapple-ipa.dtsi` (SM8650) are identical except for the IPA IRQ (655 vs
654) and `qcom,ipa-q6-smem-size`. So the upstream SM8650 node is the
template, with these changes:
- **reg:** IPA base 0x3e00000 + `qcom,ipa-cfg-offset` 0x140000 = `ipa-reg`
  0x3f40000; `ipa-shared` 0x3f50000+0x5000 (the 5.5 mem end is 0x4fd8);
  `gsi` 0x3e04000+0xfc000 (stock `reg`). All the same as SM8650.
- **Interrupts:** GIC SPI 655 (ipa) and 432 (gsi), from the stock
  `interrupts`. The SM8650 node's edge type for the IPA IRQ is kept.
  smp2p: `ipa_smp2p_in` 0/1 and `ipa_smp2p_out` 0/1. sm8750.dtsi already
  has these entries (`ipa-ap-to-modem`, `ipa-modem-to-ap`).
- **iommus:** `apps_smmu` 0x4a0 (AP) and 0x4a2 (uC), from the stock
  `ipa_smmu_ap` and `ipa_smmu_uc`.
- **Interconnects:** `aggre2_noc MASTER_IPA -> mc_virt SLAVE_EBI1` (memory)
  and `gem_noc MASTER_APPSS_PROC -> cnoc_main SLAVE_IPA_CFG` (config).
  `cnoc_main`, not `config_noc` as on SM8650: SLAVE_IPA_CFG sits in
  sm8750's `cnoc_main_nodes`, and downstream `sun-ipa.dtsi` names
  `&cnoc_main SLAVE_IPA_CFG` too.
- **Clock:** `RPMH_IPA_CLK` (sm8750 rpmhcc has it).
- **Modem tables in IMEM:** stock `qcom,additional-mapping = <0x14683000
  0x14683000 0x2000>`. That is `modem-tables@3000` (0x2000) in IMEM
  0x14680000, the same as SM8650 and Eliza. sm8750.dtsi has no IMEM node;
  `qcom,sm8750-imem` is in the imem binding. Size 0x2c000, as on SM8650 and
  Eliza.
- **Firmware:** `qcom,gsi-loader = "self"`: the AP loads `ipa_fws` with
  PAS id 15 (stock `pas-ids = <0x0f>`, upstream `IPA_PAS_ID 15`). The
  `ipa_fws.mdt` segments are relocatable, 0x8568 bytes in total. That fits
  `ipa_fw_mem` (0x9b080000, 0x10000), which upstream SM8550/SM8650 use, so
  the node uses it too. Downstream points at `ipa_gsi_mem` on both SoCs.
  `firmware-name = "qcom/sm8750/OnePlus/ipa_fws.mbn"`, copied to the phone
  from read-only `modem_a` like `modem.mbn` (mdt as `.mbn` plus the `.bNN`
  files). Firmware never goes in the repo.
- **Board:** the PR dts keeps `remoteproc_mpss` disabled. The trial
  enables it, as the gpu1 tree does. The MPSS has auto_boot off; it starts
  only through `omamobile-modem start` with recovery disabled.

### Userspace

`CONFIG_QCOM_IPA=m` and `CONFIG_RMNET=m` are already in the gpu1 config
(`QMI_WWAN` is off; it is for USB modems). With IPA up, the kernel creates
`rmnet_ipa0`, and ModemManager's qcom-soc plugin binds it to the QRTR
control port. Data then goes through an rmnet link that MM creates on top.

### Size

Small: no new driver code. It is the 3 RFC patches, one compatible line, an
sm8750 IMEM + IPA node, and the board enable. Risks:
- the RFC is untested on SM8750;
- the QMI filter-stats request is new;
- the firmware load through TZ happens at IPA probe;
- modem crash handling stays as before (recovery off, no stop).

## Trial boots

All are one-shot `fastboot boot` of a non-AVB image (`oops=panic`), modem
flag set only for the session, remoteproc recovery off, back on gpu1 after
each with a clean rootfs. Logs stay on the host (`~/android/mainline/logs/p73-ipa*`).

### ipa1 (13:39 and 13:44 CET): IPA did not probe

`ipa 3f40000.ipa: error -ENXIO: IRQ gsi not found`. The node was copied
from SM8650, whose interrupt specifiers carry a 4th cell (PPI partition).
The SM8750 GIC has `#interrupt-cells = <3>`, so the trailing 0 was parsed
as the phandle of the next entry. Fix: `20fc72915` (3-cell specifiers).

### ipa2a (13:52 CET): IPA up, modem stable, bearer connects

- `insmod ipa.ko`: "IPA driver initialized", "setup completed
  successfully" (GSI firmware loaded through TZ, PAS 15). No IPA/GSI
  errors, no oops; the 4 WARNs are the known clk WARNs from insmod.
- Modem start: IPA logs "received modem starting/running event";
  `rmnet_ipa0` appears; ModemManager lists it as the net port next to
  `qrtr0`.
- Registered on TELMORE LTE (home), packet service attached, signal 49-67 %.
- **No `DS_3GPP_BEARER_SWITCH_COMPLETE_IND` assert.** The modem stayed up
  for the whole 140 s watch and the following data test (about 3.5 min
  online in total), where without IPA it crashed after about 30 s every time.
- `mmcli --simple-connect` (APN `internet`, IPv4): bearer connected, MM
  created the mux link `qmapmux0.0` on `rmnet_ipa0` (mux id 1), static
  IPv4 /30 with gateway, two DNS servers and MTU 1500 reported by QMI.
- Ping failed (0 of 3): nothing applied the IPv4 settings. MM leaves a
  static config to the host, and systemd-networkd only logged "Failed
  while parsing properties of bearer ... No such device or address".
  Next (ipa2b, same image): bring the links up and add the address and
  /32 host routes by hand, so Wi-Fi stays the default route.

### ipa2b-ipa2h (14:02-14:48 CET): Smart Transmit license crash

Same image and rootfs as ipa2a. Times from kmsg relative to going online.

| boot | change | online | result |
|---|---|---|---|
| ipa2b, 2c | none (manual IP step added after connect, never reached) | MM | searching, crash `rtsar ... Smart Transmit License Check Failure Code (1, 1, 1)` |
| ipa2d | MM masked, modem left in low power | never | no crash for 190 s; PDC config Active; DMS time 2017-06-16 (source `device`) |
| ipa2e | NAS mode preference LTE-only (copies only) | MM | same crash |
| ipa2f | copies restored to the 12:46 backup | DMS by hand (MM sim-missing) | no crash 140 s, MM stayed failed, no RF info |
| ipa2g | none (copies as ipa2f left them) | MM | same crash |
| ipa2h | MM held until modem-up+60 s | MM at about +60 s | same crash about 20 s after online |

- Every boot online and still searching about 20 s later crashed; ipa2a
  registered about 2 s after online and survived 3.5 min with a bearer.
- tqftpserv request lists are identical in ipa2a and ipa2h; its readwrite dir
  holds only `mcfg.tmp` and `server_check.txt`.
- Leads, unproven: (1) the license check needs valid time and the modem has
  2017 until the network gives it time; (2) something written during ipa2a
  (bearer connect) changed acquisition, so the modem no longer registers fast.
- Disabling Smart Transmit is not an option: it is the RF exposure limit.
