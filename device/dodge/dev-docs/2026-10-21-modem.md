# 2026-10-21 — modem assessment (MPSS, rmtfs, IPA, ModemManager)

**Goal.** Find out what the modem DSP needs on sm8750-mainline 6.16 before
ModemManager can see a modem. Root cause first, no boot yet.
**Phone.** OnePlus 13 CPH2653 (dodge). No serial, IMEI, IMSI or number here.
**Kernel.** `6.16.0-gb3ee311dab85` (Oct 16 Image plus later modules).
**Result.** Part 1 (morning): assessment only. Part 2 (10:45-11:10 CEST): userspace
installed with its services off, read-only EFS copies made, the `rmtfs_mem` DTB
booted twice with `fastboot boot` (nothing flashed). The modem was not started.

## What we did

- Read the kernel tree, the dodge DTS, the stock live DT
  (`rooted-2026-10-15-on/live.dts`) and the stock boot log. All read-only.
- Mounted `modem_a` (vfat, `sde6`) **read-only** on the phone and copied
  `image/modem.mdt` to `/lib/firmware/qcom/sm8750/OnePlus/modem.mbn`, the
  `modem.bNN` segments (42), `modem_dtb.mdt` as `modem_dtb.mbn` with its 3
  segments, and `image/modem_pr/` (MCFG carrier configs, 30 MB) the same way.
  That is 72 MB. Unmounted afterwards. The ADSP was done the same way
  (2026-10-19). Not committed.
- Checked the partition names: `modemst1`, `modemst2`, `fsg` and `fsc` exist
  (`sdf10`-`sdf13`), and so do the OnePlus NV partitions `oplusdycnvbk` (`sdf7`)
  and `oplusstanvbk_a` (`sdf8`). **None of them was opened.**

## Risks found

- **rmtfs is the only way the modem writes EFS or NV.** Upstream rmtfs with
  `-P` writes `modemst1`/`modemst2`/`fsg`/`fsc` on request, and OnePlus adds two
  more NV partitions. That is the calibration/EFS the rules forbid touching.
  The plan is to run rmtfs only on in-RAM copies with writes dropped. Check
  rmtfs's options in the installed version first; if it can't drop writes,
  serve copies in a tmpfs and never point it at `/dev/sdf*`.
- PLAN §6 row 11 asks for NV backups first. Reading `modemst1/2`, `fsg` and
  `fsc` is allowed, but the copies contain the IMEI and NV. They stay off git
  and off this repo (owner-only, mode 600).
- Starting the modem without rmtfs makes it wait or crash. A crash is a
  remoteproc recovery, not a reboot, but a fatal error can take the SoC down,
  so the log stream and the watchdog stay on.

## Part 2 (10:45-11:10 CEST): userspace, EFS copies, rmtfs_mem

### pacman keyring

- **Cause:** `/etc/pacman.d/gnupg` did not exist. The image was never
  keyring-initialised, so pacman could not import the `omamobile` key
  ("keyring is not writable"). `/` is a normal rw ext4.
  Fix: `pacman-key --init`, then `pacman-key --populate archlinux archlinuxarm
  omamobile omarchy` (all four keyrings ship in `/usr/share/pacman/keyrings`).
- **Two more blockers:**
  - The 6.16 kernel has no Landlock, so pacman's download sandbox fails. Use
    `pacman --disable-sandbox` (or `DisableSandbox` in `pacman.conf`; not set).
  - `usb0`'s static default route (metric 0, via the laptop, which does no NAT)
    beat Wi-Fi's (metric 600), so the phone had no internet. For this session
    only: `ip route replace default via 172.16.42.2 dev usb0 metric 2000`. It is
    not persistent. The lasting fix is a higher metric in the `usb0` config.
- **Installed from `extra`:** `libqmi` 1.38.0, `modemmanager` 1.24.2,
  `libmbim`, `libqrtr-glib`, `ppp`, and `libmm-glib` 1.24.2-1 to -2. Also
  `make`, `meson`, `ninja` and `pkgconf` for building. A `--print` dry run first:
  nothing else was upgraded, so this is not a partial upgrade of the base.
  `ModemManager.service` is **masked**. (The pacman udev hook printed a harmless
  `bq27541` uevent error.)
- **Not packaged for aarch64 here**, so built from linux-msm git in
  `/root/src`: `qrtr` `29e36ae` (meson, installed to `/usr`: `libqrtr`,
  `qrtr-lookup`, `qrtr-cfg`), `rmtfs` `b30a3eb`, and `tqftpserv` `0bf5b98`
  (binaries in `/usr/local/bin`). No unit files were installed, so nothing
  starts at boot.

### rmtfs: the safe invocation

From `rmtfs.c`/`storage.c` at `b30a3eb`:

- `-r` (`storage_read_only`): `fd_open` reads the file once into a RAM shadow
  buffer with `O_RDONLY`. `storage_pwrite` only changes that buffer, and
  `storage_sync` does nothing. Nothing is ever opened `O_RDWR`.
- `-o DIR`: the image directory. Without `-P` the files are `modem_fs1`,
  `modem_fs2`, `modem_fsg`, `modem_fsc` (plus `oem_stanvbk`/`oem_dycnvbk`, the
  OnePlus NV paths; they are absent, so rmtfs rejects those requests).
- `-P`: real partitions by partlabel. **Forbidden.**
- `-s`: rmtfs starts and stops the MSS remoteproc itself. Not used; we start it
  by hand.
- `sharedmem.c` falls back to `/dev/mem` when there is no
  `/dev/qcom_rmtfs_memN`. **Only start rmtfs when `/dev/qcom_rmtfs_mem1`
  exists** (no devmem).

**Safe:** `rmtfs -r -o /var/lib/omamobile/modem-efs -v`, never `-P`. Two
layers: the files are copies, and `-r` keeps every write in RAM.

Dry run at 11:04 CEST (modem down, 10 s): `registering services`, exit by
timeout. The sha256 of `sdf10`-`sdf13` and of the copies was the same before
and after.

### rmtfs_mem DT region (step 3)

- Kernel `bd9587d65` (local): `rmtfs@d7c00000`, 4 MiB, `qcom,rmtfs-mem`,
  client-id 1, vmid `QCOM_SCM_VMID_MSS_MSA`. `d5100000-d7ffffff` is System RAM
  both on stock and on ours, and the region sits just below `tz_merged`, as on
  SM8650. The stage 2 DTB differs from the flashed one only in that node
  (checked with `dtc` and `diff`).
- Packed with the Oct 16 Image (`STAGE2_IMAGE=out-dodge/Image.oct16-b3ee311dab85`),
  `DTB_OPTS='splash fb'` and the flashed cmdline. Backup of the flashed image:
  `boot-chain-avb.before-rmtfs.img`, which matched `boot_a`'s sha256.
- **Boot r1, 10:52, fastboot boot:** SSH at 27 s, `d7c00000-d7ffffff : reserved`.
  But **the display failed from about 8.8 s**: `ctl 1 reset failure`,
  `kickoff timeout`, commit-done -110 (162 lines), and
  `systemd-backlight@…dsi` failed. Wi-Fi and BT were fine.
- **Control, plain reboot to the flashed boot_a, 10:56:** no display errors.
- **Control, 10:59, fastboot boot with the same pack minus the rmtfs node**
  (`fdtput -r`; its DTB was identical to the flashed one): no display errors at
  85 s.
- **Boot r2, 11:02, fastboot boot with the rmtfs DTB again:** clean. 0 errors at
  73 s, region reserved.
- So 1 of 2 rmtfs boots lost the display and 0 of 2 control boots did. That is
  not enough to blame the node (no-map on 4 MiB of RAM shouldn't touch the
  DPU), and not enough to call it a flake. **Not flashed for that reason.**
- On r2, `qcom_rmtfs_mem` (built at `KERNELRELEASE=6.16.0-gb3ee311dab85`;
  it was not in the module tarball) is staged in
  `/usr/local/lib/omamobile/modem/`. `insmod` gave `/dev/qcom_rmtfs_mem1`,
  `phys_addr 0xd7c00000`, `size 0x400000`, `client_id 1`, and no assign error.
- Back on the flashed boot_a at 11:05.

### Not done (step 4)

`only_adsp` is a 0444 parameter set by `adsp-battery.sh`
(`load qcom_q6v5_pas.ko only_adsp=1`). Probing the modem needs a boot with that
changed, and reloading pas at runtime would take the ADSP (battery, audio) down.
So starting the MPSS needs its own boot. Not done in this timebox.
