# 2026-10-17 — S3910 touch registers, panel driver stays off

**Goal.** Get the touchscreen onto the simpledrm desktop without
loading the held module tree.
**Phone.** OnePlus 13 CPH2653. Omarchy 4.0.4. Hyprland still up.
**Kernel.** `6.16.0-gb3ee311dab85`
**Result.** An input device named `touchpanel` appeared, and Hyprland
lists it. A finger has not confirmed an event yet.

## What we did

The in-tree driver did not build: `TOUCHSCREEN_SYNA_TCM2` depended
on I2C, and the Makefile named `syna_tcm2.o` as both the module and
a member. It now depends on SPI and builds `synaptics_tcm2`. The
fragment asks for that as a module. The running kernel was not
rebuilt. The module was compiled against it (`vermagic`
`6.16.0-gb3ee311dab85`) and insmodded.

`a90000.spi` was the only enabled SPI controller, and it was
deferred on its TX DMA channel. `gpi.ko` from the held tree cleared
that, then `spi-geni-qcom.ko`. Nothing else left the deferred list
because of those two. The touch module then bound `spi0.0`.

The three modules are copied to `/usr/local/lib/omamobile/` and
`omamobile-touch.service` insmods them before Hyprland. The held
directory was not renamed back, so `msm` stays unloaded.

## What happened

`dmesg` recorded `input: touchpanel`. The device has absolute X and
Y, plus the multitouch slot, position and tracking axes. Hyprland's
device list shows `touchpanel` under Touch. The session stayed
active. The driver warned that its SPI id table has no entry for
`synaptics,tcm-spi-hbp`; the OF match bound it anyway.

## Learning

Touch does not need the panel driver. The SPI host does need the
GPI DMA module, which was not loaded while the module tree was held.
The next boot loads these three modules and then Hyprland. A tap is
the remaining check. The VCI rail is still 1.8 V, so the panel
driver stays disabled.
