# 2026-10-26 — modem on writable EFS copies, 7.3 gpu1 (12:45-13:05 CET)

**Goal.** Follow-up to [2026-10-26-modem-nvbk-73.md](2026-10-26-modem-nvbk-73.md):
let rmtfs write the modem's EFS changes to the **copies** in
`/var/lib/omamobile/modem-efs` (never the real partitions), so the
operator MCFG can commit, then check radio, registration, signal and SIM.

**Result.** It works up to registration. After one write-and-reboot cycle the
MCFG is `Active`. With the slot-1 session provisioned and the modem set
online, it registers on **TELMORE LTE, home network** within about 6 s,
signal RSRP -105 dBm / RSRQ -7 dB / SNR 13-14 dB. No SIM reject: the SIM is
active. About 30 s after going online the modem **crashes**, the same assert
both times, because the LTE default bearer needs a data path (IPA) we don't
have. With remoteproc recovery off the crash is contained: the phone stays
up and reboots cleanly. The real partitions are byte-for-byte unchanged.

## Safety setup

- Backup of the copies dir before any write: a timestamped tar + sha256 on
  the phone (mode 400) and on the Omarchy machine outside the repo. Not in git.
- Real partitions hashed first (sha256 over the block device, read-only):
  persist, modem_a/b, oplus_sec_a/b, modemst1/2, fsg, fsc, oplusdycnvbk,
  oplusstanvbk_a/b. All had block `ro=1`. Hash list kept in the gitignored logs.
- rmtfs runs as `rmtfs -o /var/lib/omamobile/modem-efs -v` (drop-in
  [../modem/omamobile-rmtfs-rw-copies.conf](../modem/omamobile-rmtfs-rw-copies.conf),
  opt-in). Without `-P` rmtfs opens only `<dir>/<file>`, `O_RDWR` without
  `O_CREAT` (rmtfs `storage.c`). Its open fds were checked: only the four
  copies and `/dev/qcom_rmtfs_mem1`, no `/dev/disk/by-partlabel` path. Never `-s`.
- The helper now writes `disabled` to the modem remoteproc's `recovery` before
  starting it (the setting resets to `enabled` every boot). Otherwise a modem
  crash makes the kernel stop and restart the MPSS, and a stop resets the phone.
- Shutdown path checked: the omamobile units have no ExecStop that touches the
  MPSS (only the netport's `ip tuntap del`), the scripts never `echo stop`, and
  `qcom_q6v5_pas` has no `.shutdown` hook. All four reboots were clean
  (previous journal ends in systemd-shutdown sync/SIGTERM).

## The crash

```
qcom_q6v5_pas 4080000.remoteproc: fatal error received: lte_rrc_llc.c:8590:
  Assert 0 failed: DS_3GPP_BEARER_SWITCH_COMPLETE_IND not rcvd from DS in 2600ms
remoteproc remoteproc0: crash detected in modem: type fatal error
```

After LTE attach the modem's data services have to bring up the default EPS
bearer's data path, which on this SoC goes through IPA. SM8750 IPA isn't
supported in our kernel, so DS never confirms and LTE RRC asserts. It isn't a
SIM or network reject: the network accepted the attach. With recovery off the
remoteproc stays `crashed` until the next boot. **Until IPA works, any LTE
attach crashes the modem, so data, and so far a stable registration, both
depend on IPA.** Setting low-power right after registering didn't prevent it.

## SIM

- Slot 1 card present, USIM app detected, PIN1 **disabled** (no PIN).
- The primary GW provisioning session isn't created automatically: at every
  boot `Primary GW: session doesn't exist`. ModemManager then fails with
  `sim-missing` (`GW primary session index unknown`). One
  `--uim-change-provisioning-session` (slot 1, activate, the USIM AID read from
  card status) makes the app `ready`. It doesn't survive a reboot.
- No reject cause, registration accepted: the SIM is active on TELMORE.

## ModemManager "Failed to find a net port"

It's a startup race, not missing udev tags (`rmnet_mm0` has
`ID_MM_CANDIDATE`, `ID_MM_QCOM_SOC`, `ID_MM_PHYSDEV_UID=qcom-soc`).
In boot B MM built the device with 1 port. After `systemctl restart
ModemManager` (safe, it doesn't touch the remoteproc) and in boot C it built
it with **2 ports** and grabbed `net/rmnet_mm0` as the data port. Not fixed yet;
candidates: order MM after the modem's QMI services are up, or rescan once
the modem is up.

## What the copies hold now

`modem_fs1`/`modem_fs2` differ from the pre-write backup in every sector
(rewritten in full every boot, now with the MCFG commit and the TELMORE
registration state). `modem_fsg`, `modem_fsc`, `oem_stanvbk` and
`oem_dycnvbk` match their original checksums: the modem never wrote them.

## Stage 2 plan (real partitions): prepared, NOT run

Not worth doing before IPA: on the real partitions the modem would crash on
attach just the same. Steps, each needs Martin's go-ahead:

1. **Full backup** (read-only, modem not running, flag off):
   for each of `modemst1 modemst2 fsg fsc oplusstanvbk_a oplusstanvbk_b
   oplusdycnvbk modem_a modem_b oplus_sec_a oplus_sec_b` and persist
   (`/dev/sda2`):
   `ssh phone "dd if=/dev/disk/by-partlabel/$p bs=1M status=none" > backups/parts-<TS>/$p.img`,
   then sha256 on the phone and on the Omarchy machine, and compare with the
   baseline hashes. Mode 400, dir 700, outside the repo, never in git.
2. **rmtfs change.** Not `-P`: with `-P` rmtfs looks for partlabels
   `oem_stanvbk`/`oem_dycnvbk`, which this phone doesn't have (they're
   `oplusstanvbk_a`/`oplusdycnvbk`), so the NV backup and the bands would be
   lost. Instead a new dir, e.g. `/var/lib/omamobile/modem-efs-real`, with
   symlinks: `modem_fs1 -> /dev/disk/by-partlabel/modemst1`,
   `modem_fs2 -> .../modemst2`, and for now `modem_fsc`, `modem_fsg`,
   `oem_stanvbk`, `oem_dycnvbk` -> the existing copies (the modem never wrote
   those). Drop-in `ExecStart=/usr/local/bin/rmtfs -o
   /var/lib/omamobile/modem-efs-real -v`. Never `-s`. Clear `ro` on modemst1
   and modemst2 only (`blockdev --setrw`), everything else stays `ro=1`.
3. **Check:** one boot, MCFG Pending -> reboot -> Active, as with the copies.
   Only modemst1/2 hashes may change.
4. **Revert:** remove the drop-in and the flag, reboot (modem off), set the
   two partitions back to `ro`.
5. **Restore** (only with explicit approval, modem off): `blockdev --setrw`
   on the one partition,
   `ssh phone "dd of=/dev/disk/by-partlabel/$p bs=1M conv=fsync" < $p.img`,
   re-hash, must equal the backup, `blockdev --setro`.
