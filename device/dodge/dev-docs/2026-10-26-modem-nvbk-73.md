# 2026-10-26 — modem RF bands on 7.3 gpu1: the OnePlus NV backup (12:30-12:42 CET)

**Goal.** Find out why the MPSS stays `offline` with no RF bands
([2026-10-26-modem-sim-73.md](2026-10-26-modem-sim-73.md)) and get it to
radio on, registration and data.

**Result.** The cause of the missing bands is found and fixed: rmtfs couldn't
serve OnePlus's NV backup. With it in place the modem reports its full band
list. The modem then marks the operator's MCFG `Pending` and sits in
`shutting-down`, waiting for a reset to apply it. It never got as far as
radio on, so there's no registration, signal or data yet. Next step needs
Martin's decision (below).

## Root cause

- The boot journals of the earlier modem boots show rmtfs failing to open
  `/oem/nvbk/static` and `/oem/nvbk/dynamic`. Our rmtfs (linux-msm git) maps
  them to `oem_stanvbk` and `oem_dycnvbk` (linux-msm/rmtfs PR #33, merged
  2026-06), but we run it with `-o /var/lib/omamobile/modem-efs`, so it looks
  for files of those names there, and they didn't exist.
- On the phone they're the partitions `oplusstanvbk_a`/`_b` (static NV:
  OnePlus's per-RF-variant modem NV items, the same for every unit of a model) and
  `oplusdycnvbk` (dynamic: per-unit modem calibration, MAC and the like).
  Each one is 20 MiB with data in it. Without them the modem has no RF NV, which
  fits `offline`, InvalidTransition and an empty band list.
- Ruled out: persist (read-only image, mounted `ro,noload`): its `rfs/` only
  has the two server-check text files and nothing for MCFG or RF.
  tqftpserv already serves every file the modem asks for, and the modem never
  asks for `mcfg_hw`. PDC still lists 0 platform configs; that may be a
  secondary lead.

## What was done

1. Read-only copies into the rmtfs dir on the phone (block devices are `ro=1`;
   `dd if=` only; device sha256 checked before and after, identical to the
   copies; mode 600; hashes in `NVBK.SHA256` next to `SHA256SUMS`):
   `oplusstanvbk_a` -> `oem_stanvbk`, `oplusdycnvbk` -> `oem_dycnvbk`. They
   stay on the phone and are not in git (device-specific calibration).
2. Installed the repo's `omamobile-modem.service` (no ExecStop) and helper
   on the phone (old ones kept as `*.pre-nostop`), set the modem flag, gate,
   reboot (12:35 CET). rmtfs stayed `-r`.
3. Results: rmtfs opens `/oem/nvbk/static` and `/oem/nvbk/dynamic` and
   serves reads. DMS band capabilities now list GSM, WCDMA, LTE 1-71 and NR
   1-78 (none before). NAS: no service on any RAT, RF band info
   `InformationUnavailable`. DMS mode `shutting-down`, and it stayed that way
   (5 min). PDC: `TDC_Denmark_Commercial` is now `Pending` (was `Active`).
   rmtfs logged a few EFS writes (kept in RAM because of `-r`). UIM: slot 1 card
   present, application `detected`, PIN state `not-initialized` (the modem is
   shutting down). ModemManager didn't create the modem ("Failed to find a net
   port"; not looked into, MM can't do anything with a modem in this state
   anyway).
4. Safety: set `recovery` to `disabled` on the modem remoteproc (runtime
   only), so a modem crash wouldn't trigger the kernel's stop/restart, the
   path that hard-resets the phone. No crash happened.
5. Cleanup: removed the flag, gated reboot (12:40 CET): gpu1, rootfs mounted
   clean, only ADSP running, ModemManager and the modem unit inactive, all six
   EFS/NV copies match their hashes (nothing written).

## Reading

- After the NV is loaded, the MCFG auto-selection wants to (re)activate the
  operator config, and that needs a modem reset. On stock Android that
  happens once: the MPSS restarts, the EFS keeps the result, and later boots
  find it already active.
- Here it can't finish. A modem restart is the remoteproc stop that resets
  the whole phone. And rmtfs `-r` throws away the EFS writes, so every boot
  starts over and goes back to `Pending`.

## Options (need Martin's decision)

- **A (proposed):** let rmtfs write to the *copies* in
  `/var/lib/omamobile/modem-efs` (drop `-r`; never `-P`, so the real
  partitions are never touched). Back the copies up to a second directory first. Boot
  once with the modem, let it write `Pending`, then do a normal gated reboot: the
  next boot should apply the config at startup without asking for a reset.
  Risk: only the copies change; they can be restored from the backup or
  re-read from the partitions at any time.
- **B:** fix the phone reset on remoteproc stop in the kernel (trial branch),
  so the modem can restart itself (SSR) like on Android. Bigger job, needed
  anyway for a modem that survives its own crashes.
- Not done: `--pdc-activate-config`/`--pdc-load-config` (writes EFS and asks for
  the same reset).

## SIM

No sign of a SIM problem so far: the card reads, the operator is TELMORE and
PIN1 is disabled. The modem never reached a network attach, so it couldn't
reject the SIM. Whether the SIM is active can only be seen once the radio is on.
