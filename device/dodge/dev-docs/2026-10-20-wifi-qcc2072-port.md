# 2026-10-20: Wi-Fi works: QCC2072 datapath ported to 6.16

Follows [2026-10-20-wifi-datapath.md](2026-10-20-wifi-datapath.md). The
network name and password are `<redacted>` everywhere. The NM profile lives
only on the phone (`/etc/NetworkManager/system-connections/dodge-wifi.nmconnection`,
mode 600).

## Result

Connected, with autoconnect. DHCP, gateway and internet ping, DNS, and a 100 MB
download (about 47 Mbit/s) all work on `wlp1s0`, with no ath12k warnings. It
reconnects by itself after a reboot. 5 GHz networks are now visible: the
same three BSS on 5240 MHz that the laptop sees. The "no 5 GHz" problem was
the RX descriptor layout, not regulatory or RF.

About 740 changed lines in total (12 files, +740/-27), under the 1500-line
cap. It does not need the upstream `wifi7/` restructure. Every commit builds
(checked one by one). WCN7850 (`0x1107`) keeps its own hw_params, regs, HAL
ops and RX ops. No identifiers in the diff. Patches:
`~/android/mainline/patches-dodge/wifi-2026-10-20c/`.

Not ported, because 6.16 does not need it:
- **RX queue setup without the qdesc LUT:** `reoq_lut_support` is already
  false for WCN7850 in 6.16, so the TID queues already go through WMI.
- **Ring masks and CE config:** QCC2072 uses the WCN7850 tables.

The deviations from upstream qcc2072 hw_params are deliberate:
- `supports_monitor = false`: the 6.16 monitor path still parses 64-bit TLVs.
- `rfkill_pin = 0`: not wired on dodge.
- The feature bitmap is `PERST_NO_PULL | AUX_UC`, without `QDSS_CFG_MISS`.
  That bit makes peach assert.
- The firmware directory is `WCN7860/hw2.0`.

### Review against upstream before the boot

- **Register table:** generated from upstream `qcc2072_regs` and checked
  field by field (TCL +0x18; REO, SW2REO, cmd and status +0x1c; no
  `wbm_sw1_release` and no `reo1_qdesc_lut`, which are `0xdeadbeaf` here).
- **Shared HAL constants:** every `#define HAL_* 0x...` that 6.16
  `hal.h` and upstream `wifi7/hal.h` both have is equal (HP/TP and SEQ bases).
- **Descriptors:** `rx_mpdu_start_qcc2072`, `rx_pkt_hdr_tlv_qcc2072` and
  `hal_rx_desc_qcc2072` match upstream (struct text md5). The
  `RX_MPDU_START_*` and `RX_MSDU_END_*` bitfields are identical in 6.16 and
  upstream. The accessors compared token for token. The `mpdu_start` tag
  is a `le32` with `HAL_TLV_HDR_TAG`.
- **REO:** command entry size `(4 + sizeof(qcc2072 queue stats)) >> 2`,
  status `(4 + sizeof(qcc2072 status)) >> 2`, as upstream.
- **hw_params:** diffed against the upstream `qcc2072 hw1.0` entry. The
  remaining differences are fields that 6.16 lacks, plus the deviations
  above.
- **Found in review and fixed before the boot:** the QCC2072 descriptor is
  larger than the qcn9274 one. Making it a member of `union hal_rx_desc`
  would have grown `sizeof(struct hal_rx_desc)`, which the 6.16 monitor
  path uses, and that would change WCN7850 too. The QCC2072 accessors now
  cast instead, and the union is unchanged.
- The upstream tree has no other QCC2072 special cases outside `wifi7/`
  hal, hw, pci and dp_rx (GitHub code search on torvalds/linux).

## Signal

Martin's stock phone reads about -70 to -73 dBm at the same spot. The dodge
reported:

| When | Signal |
|---|---|
| During the transfers | -57 to -61 dBm, beacon average -55 to -58 |
| Right after the first association (q-1, a different AP of the mesh) | -87 dBm |

The two numbers may not be the same AP or band: the network has several APs
on 2.4 and 5 GHz, and the phone roamed between them. So the dodge is not
weaker than stock here, but this is not a like-for-like comparison.
Station-dump counters during q-2: tx retries 19, tx failed 0, rx drop
misc 8. The q-1 roam with `DISASSOC_LOW_ACK` was on a weak AP; treat it as
RF, not a driver fault.
