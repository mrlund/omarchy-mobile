# 2026-10-16 — UFS enumerates, every disk read-only

**Goal.** See the GPT from our kernel without mounting anything.
**Phone.** CPH2653, build `CPH2653_16.0.10.501(EX01)`, slot `_a`.
**Kernel.** `6.16.0-g02a028467db0` #5, built 2026-10-16 11:02 CEST.
`CONFIG_SCSI_UFS_QCOM=y`, `CONFIG_PHY_QCOM_QMP_UFS=y`. Stage 2 cmdline
includes `omamobile.ufs-probe`. `DTB_OPTS=splash`.
**Result.** SSH at 26 s. Six disks, 139 partitions, all read-only,
nothing mounted.

## What we did

`SCSI_UFS_QCOM` and `PHY_QCOM_QMP_UFS` moved from `=m` to `=y` in
`kernel/configs/omamobile-dodge.config`. `tools/dodge-try` now requires
both built in. The init's first action after the mounts is still
`blockdev --setro` on every disk, and the probe only prints `PARTNAME`,
`ro` and size.

```sh
STAGE2_CMDLINE='rdinit=/init clk_ignore_unused pd_ignore_unused panic=10 console=tty0 omamobile.ufs-probe' \
  tools/dodge-try chain
```

Image `out-dodge-rdinit/images/boot-chain.img`, sha256
`9e404a28c2c8ec519f94714573fadfb000cb69dc8949f71b4e6022e15906d6bd`.
`Booting OKAY` at 11:04:28. The partition list is
`logs/dodge-ufs-probe-20261016-110453.txt` and `dmesg` is
`logs/dodge-ufs-20261016-110453.kmsg` (neither committed).

## What happened

SSH at 26 s. `soc@0` is present. `/proc/mounts` has no `/dev/sd*`.
`/run/ufs-probe.txt` says 6 disks and 139 partitions. 145 `ro=1` lines
(the disks plus the partitions), zero `ro=0`, and the guard logged no
`FAILED to set`.

`ufshcd-qcom 1d84000.ufs` probed. It warned that `freq-table-hz` is
missing, that `vdd-hba-supply` and `vccq2-supply` are absent (it assumes
those rails are already on), that the `ufs_mem` resource is missing, and
that MCQ is disabled (`err=-19`). `scsi host0: ufshcd` followed, and the
disks appeared. The splash fault count is still 10, all at 0.130 s.

The six LUNs:

| Disk | What it holds |
| --- | --- |
| `sda` | `persist`, `metadata`, `super`, `userdata`, `hybridswap` |
| `sdb` | `xbl_a` and its config |
| `sdc` | `xbl_b` and its config |
| `sdd` | `cdt`, `ddr`, `engineering_cdt_a/b` |
| `sde` | the A/B boot chain: `abl`, `boot`, `init_boot`, `vendor_boot`, `dtbo`, `vbmeta`, `recovery`, `modem`, `bluetooth`, `splash` |
| `sdf` | `oplusreserve1`–`5`, `modemst1`, `modemst2`, `fsg`, `fsc` |

`boot_a` is `sde12`, `init_boot_a` is `sde30`, `vendor_boot_a` is
`sde23`, `persist` is `sda2`, `userdata` is `sda15`. Slot B's copies are
on the same LUNs. Sizes for `boot`, `init_boot`, `vendor_boot`, `dtbo`,
`recovery` and `persist` match the 2026-10-15 `getvar` sizes. Nothing
on these disks was read or written.

## Learning

Fastboot `getvar` on 2026-10-15 did not list `modemst1`, `modemst2`,
`fsg` or `fsc`. The GPT names all four, on `sdf`. There is still no
partition named `efs`. Those four, plus `persist`, stay unread until a
radio plan says otherwise (PLAN.md §3.2).

The storage half of phase 3 is met: our kernel, SSH, storage visible
and read-only, nothing flashed. The framebuffer console was still open
at this point. It was met later the same day: the panel shows the Tux
logos and the kernel log
([2026-10-16-framebuffer.md](2026-10-16-framebuffer.md)). A flash of
the boot images is phase 4 and waits for an explicit yes.
